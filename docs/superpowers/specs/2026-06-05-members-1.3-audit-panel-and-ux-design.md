# Members — Sub-phase 1.3: Audit panel + UX guidance

## Context

After 1.1 (NameDialog removed, merge tool extended) and 1.2 (PIC pickers strict + email→name resolve), new fragmentation is hard to introduce. But:

1. **Owner can't see what's already fragmented.** PIC names that are orphaned (typos, legacy free-text, external people typed before they signed in) sit in the data without surface. The owner has to discover them by browsing tasks/RAID/etc. — too easy to miss.
2. **Mental model isn't unified.** Project Settings still has a "Team Members" tab with a manual add row, sitting alongside the separate "Manage Members" RBAC modal. Owners aren't sure which to use, and the relationship between the two isn't explained.

Sub-phase 1.3 fixes both.

## Goal

Two complementary additions inside `ProjectSettingsModal`'s existing Team Members section:

- **A. UX guidance banner** at the top of the section explaining the recommended flow: grant access via "Manage Members"; the manual list below is for non-RBAC external contacts only.
- **B. "PIC names in this project" audit panel** below the manual list — surfaces every unique PIC string the project actually uses, categorizes each as ✅ known or ⚠ orphan, and offers a one-click merge against a suggested canonical name (reusing 1.1's `performLegacyMerge`).

## Non-goals (deferred to Phase 2)

- Retiring the manual `project.teamMembers[]` add row entirely (user picked "keep + de-emphasize" — back-compat preserved for external contacts not yet signed in).
- Schema migration to email-keyed PIC fields (Phase 2).
- Fuzzy "Did you mean…" with Levenshtein (1.2 deferred; not revisited here).
- Audit panel for activity log (server-validated email, intentionally separate).

## Decisions (confirmed with requester)

- Keep the manual "add Team Member" row, but visually de-emphasize and reframe its purpose.
- Add the audit panel as a new sub-section under Team Members in the same modal.

---

## Part A — UX guidance banner

### Placement

Inside `ProjectSettingsModal`'s "Team Members" tab/section, at the very top, BEFORE the existing add-member row.

### Content

Two-line info banner (TOK.bg background, small icon, two paragraphs of text):

> **👥 How members work in this project**
>
> To grant **access**, click **Manage Members** in the top toolbar (RBAC). Anyone with access automatically appears in PIC autocomplete elsewhere — you don't need to re-add them here.
>
> The list below is for **external contacts not yet signed in** (vendors, advisors). Add them so their name autocompletes in PIC fields and emails. They will NOT get access until you also add them via Manage Members.

### Behavior

- Banner is purely informational, no buttons.
- Always visible to project owners + workspace owners. Hidden for read-only viewers (matches the existing edit-permission pattern of the modal).
- Single visual style: muted background, small icon, body text, no dismiss control (it's persistent guidance, not a one-time tour).

## Part B — "PIC names in this project" audit panel

### Placement

New sub-section below the existing manual Team Members list, BEFORE the Contributor Registry section. Owner-only (workspace owner OR project owner; same gating as merge tool).

### Data collection

A new pure helper `collectProjectPicNames(project)` walks the project document and returns a `Map<string, { count: number, sources: string[] }>` keyed by lowercased name (for dedup), with each entry recording:

- `name` — the original-case version (first seen)
- `count` — how many times the string appears
- `sources` — array of human-readable labels (e.g. `'task.pic'`, `'raid.owner'`, `'mitigation.pic'`, `'decision.decidedBy'`) — used in the row tooltip so owner sees WHERE this name comes from

Walks all identity reference sites (the same 10+ fields the 1.1 merge tool now rewrites): `task.pic`, `task.contributors`, `task.checkIns[].author`, `task.updates[].author`, `task.updates[].resolvedBy`, `actionItem.pic`, `actionItem.decidedBy`, `actionItem.subtasks[].pic`, `actionItem.updates[].author`, `decision.decidedBy`, `decision.author`, `raid.owner`, `raid.createdBy`, `raid.approvedBy`, `raid.validationOwner`, `raid.history[].author`, `mitigationActions[].pic`, `project.projectLead`, `project.weightChangeLog[].by`.

### Categorization

For each unique name, classify:

- **✅ Known**: matches (case-insensitive) either a `project.teamMembers[]` entry name OR a `project.memberIds[]` entry resolved through the user directory (the same lookup `deriveTeamMembers` does).
- **⚠ Orphan**: doesn't match either.

Categorize using `categorizePicName(name, teamMembers, directory, memberIds)` — a small pure helper alongside `resolvePicValue`.

### Suggestion logic for ⚠ orphans

For each orphan, compute a single suggested canonical name to merge into:

1. **Email match**: if the orphan looks like an email (`includes('@')`), find a member with that email. If exactly one match → suggest that member's name.
2. **Email-prefix match**: if the orphan is short and matches a member's email-prefix (`email.split('@')[0]`) — e.g. orphan `hattt4` matches member with email `hattt4@smartosc.com` → suggest that member's name.
3. **Substring match**: if the orphan is a substring of a single member's name (case-insensitive) → suggest that member. If 2+ matches → no suggestion (user picks manually).
4. **No suggestion**: orphan stands alone. Show only the ⚠ chip + the "Merge into..." manual dropdown.

### Render — table-like rows

```
PIC names in this project (12)
┌────────────────────────────────────────────────────────────────────┐
│  ✅ Hà Trương Thị Thu                          15 occurrences      │
│  ✅ Trang Vu Kieu                              3 occurrences       │
│  ⚠  hattt4                  → Suggested: Hà Trương Thị Thu  [Merge]│
│  ⚠  hattt4@smartosc.com     → Suggested: Hà Trương Thị Thu  [Merge]│
│  ⚠  Outsider Inc            (no match)                      [▾]   │  ← dropdown to merge manually
│  ⚠  BOD                     (group name — leave or add to roster) │
│  …                                                                  │
└────────────────────────────────────────────────────────────────────┘
[Show ✅ known] [Hide ✅ known]   ← toggle to focus on orphans only
```

Each row:
- Status badge (✅ / ⚠) on the left
- Name (truncated if very long, full in tooltip)
- Count + sources (tooltip)
- For ⚠ with suggestion: `→ Suggested: {name}` + `Merge` button (primary style) — click calls `performLegacyMerge({ from: orphan.name, to: suggested.name, email: suggested.email })`
- For ⚠ without suggestion: a small dropdown listing all teamMembers as merge targets, plus an option "Add to Team Members" (writes a new manual entry `{ name: orphan.name, email: '' }` so it stops being flagged)

### Toggle: Show / Hide known

By default, ✅ rows are collapsed to a single line: `✅ 8 known names`. Click to expand. ⚠ orphans are always shown expanded — they're the actionable items.

### Empty state

Project with no PIC names yet: render `No PIC names in this project yet — add tasks or actions to see them here.`

### Refresh

After a merge succeeds (via `performLegacyMerge`), `ProjectSettingsModal` re-renders from the updated `project` prop, the helper re-walks, and the orphan disappears (or its count drops). No manual refresh.

- [ ] `categorizePicName(name, teamMembers, directory, memberIds)` exists, returns `'known' | 'orphan'`.
- [ ] Suggestion logic implemented as a third pure helper (e.g. `suggestMergeTarget(orphanName, teamMembers)`), with 3 tiers (email, email-prefix, single substring) → returns `{ name, email } | null`.
- [ ] UX banner renders at the top of the Team Members section with the two paragraphs of guidance.
- [ ] "PIC names in this project" panel renders below the manual Team Members list, owner-only.

- [ ] ⚠ rows show suggested merge target (when one exists) with a Merge button; clicking calls `performLegacyMerge` and the row disappears on success.
- [ ] ⚠ rows without suggestion show a dropdown to pick merge target manually, plus "Add to Team Members" action that appends to `project.teamMembers[]` (reusing existing add path).
- [ ] Sources tooltip shows where each orphan came from (e.g. `task.pic, raid.owner`).
- [ ] After merge, panel re-renders without the merged orphan.
- [ ] No backward-compat breakage: the existing manual add row + Members modal + Related parties tab all work identically.
- [ ] `npm run build` clean.

## Risks

- **Walking 19 identity sites**: easy to miss one. The helper must mirror the 1.1 merge tool's coverage exactly — if either is updated, the other should be too. Add a code comment cross-referencing.
- **Performance**: walking a project with many programs/tasks/RAID items O(n) — fine for typical project sizes (<1000 tasks). Cache via `useMemo` keyed on `project` reference.
- **"Group" names like BOD / Legal**: these intentionally aren't real members; they're contributor-registry groups. The panel will flag them as ⚠ orphans, which is technically correct but noisy. Mitigation: if a name is in `project.contributorRegistry[]`, classify as ✅ Group (third category, neutral icon — not green ✅, not orange ⚠). Keeps the panel honest without nagging.
- **Email-prefix heuristic false positives**: e.g. orphan `tr` could match `trangvk@…` prefix but also `tran-test@…`. Only suggest when exactly one member has that prefix; otherwise no suggestion.
- **Manual `setMembers` write for "Add to Team Members" action**: must use the same write path the existing add row uses, so `onSave` flow consistency is preserved.
