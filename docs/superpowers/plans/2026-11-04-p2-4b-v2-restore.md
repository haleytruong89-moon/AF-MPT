# P2.4b — Admin Restore of a v2 Project Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Admin SDK CLI, `scripts/p2-restore.mjs`, restores **one** v2 project (`schemaVersion 2`) from an in-app Backup JSON, with a read-only preview, a hash-gated apply, a local snapshot of the live state written before any write, and no task ever deleted.

**Architecture:**
- **Pure core** in `scripts/lib/`, unit-tested with Vitest:
  - `restore-target.mjs` reads the project out of the Backup JSON, normalises it like the migration did, and builds the **target tree**: the backup tree plus every live item the backup lacks (the "retained" items; tasks set to `Dropped`, actions to `Cancelled`).
  - `restore-plan.mjs` splits the target with `splitProject`, diffs it doc by doc against the live v2 docs (create / update only — never delete), keeps the live v2-only fields (roles, uids, `authorUid`), reports losses, and hashes the plan. It also builds the snapshot file and the expected after-state for verify.
- **I/O shell** in `scripts/p2-restore.mjs` (Admin SDK, emulator-tested on CI). Order of writes:
  1. Read everything, rebuild the plan, require `planHash === --expect` (else `PLAN_CHANGED`).
  2. Write the local snapshot file `p2-restore-before-<pid>-<stamp>.json` (Backup JSON shape, so the same script can restore it).
  3. **One** Admin transaction: re-read the project doc and all sub-docs, require the live fingerprint to equal the preview's (else `STATE_CHANGED`, nothing written), then write every op with `version + 1` / `updatedBy: 'p2-restore'`, the project-doc patch, one restore activity event and the restore record.
  4. Read back and verify against the expected after-state.
- `schemaVersion`, `memberIds`, `memberUids`, `roles`, `visibility`, `ownerUids`, the frozen v1 arrays and existing activity are never written.

**Tech Stack:** Node ESM scripts, `firebase-admin` 12 (emulator via `FIRESTORE_EMULATOR_HOST`), `@firebase/rules-unit-testing` 4.0.1 (client checks), Vitest 2.1.9, SheetJS for the preview workbook.

**Spec:**

- `docs/superpowers/plans/2026-10-24-p2-4-switch-real-projects.md`: Ruling P4-12 (this script is the gate before wave 2), P4-4 (migration record), P4-7 (rollback edit detection), Global Constraints.

## Global Constraints

- **Nothing in this plan writes production Firestore.** Unit tests run locally; emulator tests run on CI only (no Java locally). Production runs follow the Task 6 runbook, each after an HOD-approved preview.
- **One project per run.** Every path the script reads or writes is under `workspaces/main/projects/<pid>`, plus `workspaces/main/members`, `workspaces/main/invites` (read) and `workspaces/main/restores/<restoreId>` (write). A test asserts a second project is byte-identical after apply.
- **Never written:** `schemaVersion`, `memberIds`, `memberUids`, `roles`, `ownerUids`, `visibility`, `deletedAt`, `rev`, `writeId`, the frozen v1 arrays `programs` / `actionItems` / `decisions` on the project doc, any existing activity doc, any doc of another project.
- **Never deleted:** no `delete` op exists in a restore plan (Ruling P4b-3).
- **Stamps:** created sub-docs `version: 1`; updated sub-docs `version: <live version> + 1`; both `updatedBy: RESTORE_STAMP`, `updatedAt: FieldValue.serverTimestamp()`. Project doc patch adds `updatedAt` only (it has no `version`, as with `execV2Save`).
- **Constants** (exported from `scripts/lib/restore-plan.mjs`):
  - `RESTORE_STAMP = 'p2-restore'`;
  - `RESTORES_PATH = (restoreId) => \`workspaces/main/restores/${restoreId}\``;
  - `restoreIdOf = (pid, planHash) => \`${pid}_${planHash}\``;
  - `MAX_TX_OPS = 450` (sub-doc ops + project patch + event + record);
  - `TASK_DROPPED = 'Dropped'` (App `STATUSES`), `ACTION_CANCELLED = 'Cancelled'` (App `ACTION_STATUSES`);
  - re-use `SUBCOLS`, `MAX_PROJECT_DOC_BYTES` from `scripts/lib/migrate-checks.mjs`.
- **Exit codes** for `p2-restore.mjs`: `0` ok or nothing to restore; `1` usage error, blocked, `PLAN_CHANGED`, `STATE_CHANGED`; `2` verify mismatch after commit (no automatic undo, as P4-14); `3` refused because history would be lost and `--allow-history-loss` was not given.
- **Outputs are people data, never committed.** `p2-restore-preview-<pid>.xlsx` is covered by `p2-*.xlsx`; Task 3 adds `p2-restore-*.json` to `.gitignore`. Tests write to `os.tmpdir()` only.
- **App.jsx untouched.** The only `src/` change is adding `export` to four existing names in `src/planV2Save.js` (Task 2); behaviour identical.
- **Lint:** at most 6 errors / 63 warnings. No shebang. The CLI checks the key file before any Firestore access.

## Rulings (decided while writing this plan, 04/11/2026)

Each ruling: decision — why — cost if wrong.

- **Ruling P4b-1: input is the in-app Backup JSON** `{ meta, projects, activity }`; the script takes `projects[pid]`, strips `__v2`, and runs it through `normaliseForV2(…, { pid })`.
  - **Why:** it is the only backup HOD makes (Spark: no PITR). Normalising gives a pre-migration (v1) backup the same deterministic ids the migration gave (P4-2), so unchanged items match their v2 docs.
  - **Cost if wrong:** an item edited between that backup and the migration gets a new id: the old doc is retained (Dropped) and the backup version is created. Visible in the preview (`idMap` lines).
- **Ruling P4b-2: restore = backup tree + retained live items.** Every live program / workstream / task / action / decision whose id is absent from the normalised backup is kept: a retained task is appended to the end of its live workstream (the workstream, and its program, are retained too when the backup lacks them); a retained action is appended to `actionItems`; a retained decision to `decisions`.
  - Retained **tasks** get `status: 'Dropped'` (unchanged when already `Dropped`). Retained **actions** get `status: 'Cancelled'` (unchanged when already `Cancelled` or `Done`). Retained programs, workstreams and decisions are kept unchanged.
  - **Why:** CLAUDE.md forbids hard-deleting tasks; Dropped is the app's own "removed". Re-attaching at tree level keeps `assemble(split(target))` exact and leaves no orphans.
  - **Cost if wrong:** after a restore the project shows extra Dropped/Cancelled items HOD may clean up in the app. A Completed task set to Dropped loses credit; the preview lists each one with its live status (`was Completed`) so HOD sees it before approving.
- **Ruling P4b-3: a restore plan has no delete op.** Live docs with no counterpart in the target (only possible for a RAID doc whose program has no `raid` key in the backup) are left as they are and listed as `kept`.
  - **Why:** every delete is irreversible from the snapshot alone and none is needed for "back to a point".
  - **Cost if wrong:** a stray RAID doc can stay; it is listed and HOD can clear it in the app.
- **Ruling P4b-4: live v2-only fields win.** Overlay per doc with the planner's own rules: workstream `leadUid/start/end`, program `pmUid/deputyUid/start/end` (`KEEP_WS`, `KEEP_PROGRAM`), task/action `picUid/picEmail` when `pic` is unchanged, `contributorUids` when `contributors` is unchanged, entry `authorUid` carried from the live entry (`carryDoc`). A changed `pic` is resolved with the live directory; unresolved → `picUid: null` and warning `pic-unresolved`.
  - **Why:** the backup has no roles or uids (the App value strips them); restoring would wipe PM / Sub-PM assignments. Reusing the planner's exported helpers keeps one definition.
  - **Cost if wrong:** a role change made after the backup survives the restore. HOD fixes roles via assignments, the normal route.
- **Ruling P4b-5: access fields are never restored.** `memberIds`, `memberUids`, `roles`, `visibility`, `ownerUids` stay live. The preview prints them as `unchanged (not restored)` with counts, plus any `memberIds` key found in the backup as an informational diff.
  - **Why:** access is managed by Owner/MembersModal; a backup is a content snapshot. Granting or revoking access by restore would be a silent permission change.
  - **Cost if wrong:** HOD re-adds/removes a member by hand.
- **Ruling P4b-6: history loss is refused unless `--allow-history-loss`.** For each doc the plan updates, compare entry lists live → next: task `updates`, `checkIns`; action `updates`; RAID `items` and each item's `history` and `mitigationActions[].comments`. An entry is lost when it is in the live list and not in the next (by `id`; id-less by `stableJson` without `authorUid`). Any loss → `refused: 'history-loss'`, exit 3, with the full list (doc, list path, count, entry ids/first 60 chars).
  - **Why:** the data feeds performance scoring; comments added after the backup are evidence. The App refuses the same thing (Ruling AA); the script needs an explicit, hash-covered flag.
  - **Cost if wrong:** HOD re-runs with the flag; lost entries remain in the snapshot file.
- **Ruling P4b-7: activity is append-only here.** Existing activity docs and the backup's `activity[pid]` are never written; the preview shows the backup's entry count as `not restored`. The apply adds **one** event doc `projects/<pid>/activity/restore_<planHash>`: `{ id, type: 'project_restore', description: 'Restored from backup <basename> (sha <12 hex>) by Admin script', author: RESTORE_STAMP, authorName: 'Restore (Admin script)', authorUid: null, timestamp: <ISO>, createdAt: serverTimestamp(), projectId, workspaceId: 'main', restoreId }`.
  - **Why:** DESIGN risk #13 — the v1 restore rewrote author history. One event keeps the feed honest about what happened.
  - **Cost if wrong:** activity entries deleted from the live feed stay deleted (the feed is append-only by rules, so this does not happen through the App).
- **Ruling P4b-8: one Admin transaction per restore, ≤ `MAX_TX_OPS` writes.** Over the cap → blocked `too-many-ops`.
  - **Why:** a half-applied restore is worse than none; the largest project (CRP, 187 tasks) is well under the cap. A transaction also gives the concurrency check for free.
  - **Cost if wrong:** a future large project needs chunking with per-doc version preconditions (a later plan).
- **Ruling P4b-9: two gates.** (a) `--expect <planHash>`: the hash covers pid, backup file sha256, flags, every op (kind, op, id, expectVersion, data), the project-doc patch, the retained/loss lists and the **live fingerprint**. Apply recomputes it from a fresh read; different → `PLAN_CHANGED`. (b) Inside the transaction the live fingerprint is recomputed from transactional reads; different → `STATE_CHANGED`.
  - Live fingerprint = sha256 of `stableJson({ meta: projectDoc minus updatedAt, docs: { kind: [[id, version, sha256(stableJson(data minus updatedAt))]] sorted by id } })`.
  - **Why:** any client save between preview and apply (including one that does not change the plan) invalidates HOD's approval. Same model as the flip guard (P4-5) and rollback hash (P4-16).
  - **Cost if wrong:** busy projects need a short freeze (runbook) and a re-preview.
- **Ruling P4b-10: snapshot before any write, in Backup JSON shape.** File `p2-restore-before-<pid>-<stamp>.json` = `{ meta: { projectIds: [pid] }, projects: { [pid]: appValueFromV2(assembled live, pid, 0) minus __v2 }, activity: {}, restoreSnapshot: { kind: 'p2-restore-snapshot', pid, planHash, fingerprint, backupFile, backupSha256, createdAt, docs: toJsonable(raw live docs incl. versions), meta: toJsonable(raw project doc), ops } }`. Written after the `PLAN_CHANGED` check and before the transaction. If the transaction does not commit, the CLI prints that the file is void (as `lostReportVoid`).
  - **Why:** the restore itself becomes reversible with the same script (`--backup <snapshot>`), and the raw docs cover anything the tree shape cannot (versions, stamps). This file is also the run's manifest — no second file.
  - **Cost if wrong:** reversing a restore leaves items the first restore **created** as retained Dropped/Cancelled (they are absent from the snapshot); HOD sees them in the reverse preview.
- **Ruling P4b-11: restore record** at `RESTORES_PATH(restoreIdOf(pid, planHash))`, written in the same transaction: `{ pid, planHash, fingerprint, backupFile (basename), backupSha256, snapshotFile (basename), allowHistoryLoss, counts: { create, update, retained, droppedTasks, cancelledActions, historyLost }, at: serverTimestamp(), by: RESTORE_STAMP }`. No rules `match` covers `workspaces/main/restores/**`, so clients are denied by default (emulator test).
  - **Why:** an audit trail in Firestore, not only on one laptop; deterministic id makes a duplicate run detectable.
  - **Cost if wrong:** one admin-only doc per restore.
- **Ruling P4b-12: re-run is idempotent.** After a successful apply, a preview with the same backup yields 0 ops and no patch → mode `noop`, exit 0, nothing written (no snapshot, no event, no record). A refused or failed apply writes nothing in Firestore and can be re-run from the preview.
  - **Why:** "if it exists, skip it" (spec §9).
- **Ruling P4b-13: preconditions.** Blocked (exit 1, nothing written) when: `not-found`; `deleted` (`deletedAt`); `not-v2` (`schemaVersion !== 2`); `backup-invalid` (no `meta`/`projects`); `pid-not-in-backup`; `raid-not-array` in the backup; `round-trip` (`assemble(split(target))` ≠ target); `live-orphans` (assembling the live docs reports orphans); `too-many-ops`; `doc-too-large` (live project doc + patch ≥ `MAX_PROJECT_DOC_BYTES`). Warnings: `name-differs`, `ids-generated`, `nulls-removed`, `pic-unresolved`, `migration-rollback-affected` (a migration record exists: after this restore, `p2-migrate --rollback` will report these docs as v2 edits and refuse without `--force-with-report`; and a rollback returns to the frozen pre-migration v1 tree, not to this restore).
  - **Why:** a pilot copy (no migration record) is a valid target for rehearsal; only `schemaVersion` matters.
- **Ruling P4b-14: export, don't copy, the planner helpers.** `src/planV2Save.js` gains `export` on `carryDoc`, `overlay`, `META_SKIP`, `KEEP_PROGRAM` — nothing else.
  - **Why:** the restore must keep exactly the fields the App save keeps; two copies would drift.
  - **Cost if wrong:** none at runtime; a later refactor of the planner must keep these exports.

## Review Focus

1. **A colleague saves a task between HOD's preview and the apply.** Apply must refuse (`PLAN_CHANGED` before the snapshot, or `STATE_CHANGED` inside the transaction), write nothing in Firestore, and a fresh preview must show a new hash. *(Task 4, test RS-3.)*
2. **The backup predates tasks added in v2, one of them Completed with updates.** The task must remain, now `Dropped`, with its updates intact; the preview must list it as `was Completed`. *(Task 1, test T-2; Task 4, RS-1.)*
3. **The backup predates comments on a kept task.** Default refuses with exit 3 and lists the lost entries; with `--allow-history-loss` the snapshot file holds them before the write. *(Task 2, test P-4; Task 4, RS-4.)*
4. **The backup was taken before migration (v1 shape: id-less task, duplicate `t1`).** The ids must match the migrated docs (no spurious Dropped + create pairs for unchanged items). *(Task 1, test T-4.)*
5. **PM / Sub-PM assignments and `authorUid` set after the backup.** They must survive the restore unchanged. *(Task 2, test P-3; Task 4, RS-1.)*
