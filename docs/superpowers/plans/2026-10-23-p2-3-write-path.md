# P2.3 — v2 Write Path Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `schemaVersion: 2` project becomes **writable** through the same `saveProject(tree)` call App.jsx already makes.
- The shim diffs the new tree against what it loaded and writes **only the changed docs**.
- All writes go in one transaction that checks each doc's `version`. The server rules decide who may write what.
- A **role pilot** on a copy of Treasury 2026 with real PM/Sub-PM/Assignee accounts proves it before P2.4.

**Architecture:**
- **Pure planner** `planV2Save(loaded, nextTree, ctx)`:
  - Calls `splitProject(nextTree)` and compares every doc to the loaded snapshot.
  - Emits creates, updates and deletes. Each update carries the expected `version`.
- **Executor in the shim:** one `runTransaction`.
  - Re-reads each touched doc and compares its `version` with the expected one; a mismatch is a conflict.
  - Otherwise writes with `version + 1`, `updatedBy = uid`, `updatedAt = serverTimestamp()`.
  - Updates the snapshot after success.
- **Activity** on v2 projects becomes one doc per event in `activity/{autoId}`.
- **App.jsx** keeps its in-memory tree. Its only changes are status mapping and banner copy.

**Tech Stack:** JS/TS, Firestore client SDK (transactions), rules + `@firebase/rules-unit-testing` (emulator, CI), Vitest.

**Spec / binding contract:**
- spec v2 §4, §7, §9;
- `docs/superpowers/plans/2026-10-23-p2-roadmap.md`, sections "Contract fixed by P2.1" and **"P2.3 must pick up"**. Every item there maps to a task below.

## Global Constraints

- **Ruling Q (23/10): Decisions move to `projects/{pid}/decisions/{decisionId}`.**
  - The doc holds the v1 decision object, plus `{ workspaceId, projectId, order, viaProgramId?, viaWorkstreamId?, version, updatedBy }`.
  - Writers: Owner, PM/Deputy of `viaProgramId`, or lead of `viaWorkstreamId` in the same project. These are the same claims RAID uses (Q1).
  - Reason: the v2 project doc is Owner-only, and Q1 lets PM/Sub-PM write Decisions.
  - The v1 `decisions[]` array stays frozen in the project doc, like `programs`.
- **Ruling R (23/10): appended entries carry `authorUid`.** These are `updates[]` on tasks and actions, `checkIns[]`, RAID `items[].history[]`, and mitigation `comments[]`.
  - The planner stamps `authorUid = uid` on each **new** entry. Existing entries are never touched.
  - Rules require that every entry appended by the caller has `authorUid == request.auth.uid`. App.jsx ignores the extra key.
  - **As implemented (Ruling T):** App.jsx prepends, so rules check suffix-preserving append-only and at most one new entry per write, at index 0, with `authorUid == caller`. Rules check this only on top-level lists (task `updates`/`checkIns`, action `updates`); nested RAID `history[]`/`comments[]` rely on planner stamping. A manager's same-size rewrite can change authorship, so `authorUid` is trustworthy for assignee/contributor/PIC entries only. k > 1 new entries in one save are split into k transactions (Ruling X).
- **Every v2 write must:**
  - stamp `updatedBy = uid` and bump `version` (enforced since P2.1);
  - never hard-delete a task (CLAUDE.md). The planner **refuses** a plan that deletes a task doc.
  - Workstream and action deletes follow the role matrix.
- **The client never decides permissions.** The planner writes what changed. On a rules denial the whole transaction fails, and the banner shows which item kinds were refused. UI gating by role is P4.
- **No mass App.jsx refactor.** Allowed edits:
  - `saveProject` / `appendActivity` status mapping;
  - SaveBanner copy for `denied`;
  - a one-line info toast when a v2 project loads with orphans (Owner only).
- **Production data writes:** only the role-pilot copy, via preview → HOD approval → `--apply` → `--rollback`.
- **Lint and scripts:** lint ≤ 6/63; no shebang; gitignore any new output.

## Review Focus

1. **Two people edit two different tasks of the same project at the same time.** Both saves must succeed; the per-doc `version` is the concurrency unit. Two people edit the **same** task: the second save gets a conflict.
2. **A save that touches items the user may not change.** For example, an Assignee drags a task to another workstream. The whole save is refused, no partial write, the banner says so, and the tree reloads cleanly.
3. **Mark done by an Assignee** (A4). It is refused; the banner tells them their Sub-PM or PM closes tasks until P3.
4. **Activity append and RAID/Decision edits by PM/Sub-PM** must pick the right `via*` claim automatically from the user's role in the edited program or workstream.
5. **A v1 project's load and save path is byte-for-byte unchanged.**

### Task 3: Pure save planner

**Files:**
- Create: `src/planV2Save.js`
- Test: `tests/unit/planV2Save.test.js`

**Interfaces:**
- `loaded` = `{ meta, docs: { workstreams, tasks, actions, raid, decisions } }`. Each kind is a `Map<docId, { version, data }>`, taken from the read path.
- `planV2Save(loaded, nextTree, { uid, wid, pid, roleHints })` → `{ ops: Array<{ kind, op: 'create'|'update'|'delete', path, data?, expectVersion? }>, metaPatch?, refused?: string }`.
  - **Diffing:** compare the `data` from `splitProject(nextTree)` with the loaded `data`, ignoring `version` / `updatedBy` / `updatedAt` / `order`-only moves. A move inside one workstream is an update.
  - **New appended entries** get `authorUid` (Ruling R).
  - **`via*` claims** for RAID and decisions are chosen from `roleHints`, in this order: Owner → PM of the program → lead of a workstream in that program → `null`. `roleHints` comes from the loaded `programMeta` and the workstream docs, evaluated against `uid`.
  - **`metaPatch`:** the project-doc fields that changed (Owner-only by rules).
  - **Task deletes:** `refused = 'task-delete'` when the plan would delete a task doc.

  - Appended update gets `authorUid`; existing updates untouched.
  - RAID edit by a lead picks `viaWorkstreamId`; by a PM picks `viaProgramId`.
  - Project name change → `metaPatch`.

### Task 4: Shim executor, v2 activity, App status mapping

**Files:**
- Modify:
  - `src/storage-shim.ts`
    - **v2 read:** keep `loaded` per pid, with versions; also read the `decisions` sub-collection.
    - **v2 save:** when the doc is v2, run `planV2Save`, then one `runTransaction`. It `get`s every op target, and a version mismatch or unexpected existence is a conflict. Otherwise it applies the ops with `version: expect+1` (creates `1`), `updatedBy`, `updatedAt`. It applies `metaPatch` with an `update` on the project doc. After that it refreshes `loaded` from the written data. It returns `ok` / `conflict` / `denied` (permission-denied from the commit) / `error`.
    - **v2 activity:** on `set('activity:pid', array)`, append each entry not yet known as `activity/{entry.id}` with `authorUid`, `createdAt: serverTimestamp()`. On `get`, read the newest 500 by `createdAt`, mapped to the v1 array shape.

  - `src/App.jsx`:
    - `saveProject` maps `denied`.
    - SaveBanner `denied` copy: “Some changes to “{name}” were not saved: you don’t have permission for them. Closing a task needs your Sub-PM or PM.”
