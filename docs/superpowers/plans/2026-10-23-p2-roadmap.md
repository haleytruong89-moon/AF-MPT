# P2 — Server-side permissions: roadmap

P2 implements spec v2 §7–§9 (`docs/superpowers/specs/2026-10-14-roles-permissions-v2-design.md`). It is too large for one plan, so it ships as five sub-plans. Each one is a few small PRs and has its own gate. Each sub-plan is written in full only when the one before it has passed its gate, because later sub-plans depend on what the earlier ones teach us.

## HOD decisions (23/10/2026)
- **Q1:** Decisions and RAID stay in the project doc. Owner and any PM/Sub-PM of the project may write them.
- **A2/A3:** each program has 1 PM, with an optional Deputy PM who has the same rights. Each workstream has 1 Sub-PM; when it is empty, the PM covers it.
- **A4:** in P2, rules stop an Assignee from setting `Completed` or `Dropped`. Between P2 and P3, PM/Sub-PM close tasks; P3 adds "Submit as done" and the Approvals inbox.
- Earlier decisions still apply (spec §2.1): identity by uid, `ownerUids[]`, projects `restricted` by default, `wid` variable, rules tested on CI before every deploy.

## Contract fixed by P2.1 (binding for P2.2–P2.4)
Decided during P2.1 execution (23/10/2026). Each later sub-plan must cite this section.

- **Program data lives in `programMeta`.** Ruling C: `programMeta[programId]` holds every v1 program key except `workstreams` (name, raid, …) plus `order`, `pmUid`, `deputyUid`, `start`, `end`. The v1 `programs[]` and `actionItems[]` arrays in the project doc stay frozen for rollback and are never read in v2. `assembleProject` returns `{ project, orphans }`, and the read path must surface non-empty orphans.
- **Every v2 write must:**
  - stamp `updatedBy` with the writer's uid (Ruling I, enforced by rules);
  - set `version` to 1 on create and to `version + 1` on update (Ruling H, enforced). This includes an Owner restore/import over existing v2 docs.
- **Identity:** rules key on `picUid` only. `picEmail` is display and lookup data for invite-only people.
- **Owner checks:** Owner = uid in `ownerUids` OR the legacy `workspaceOwner` email until P2.5. In-app Transfer ownership stays locked while `ownerUids` is set (Ruling D); transfers go through the admin script until P2.5.
- **P2.4 checklist:**
  - Put every assigned `pmUid`, `deputyUid`, `leadUid` and every `picUid` into `memberUids` of restricted projects. Otherwise they can write but not read.
  - Doc ids for items without an id depend on position. Make the migration idempotent by keying on content or by recording the mapping.
  - The count report must also flag Owner-written tasks whose `programId` / `workstreamId` do not match a workstream doc.
- **RAID moves out of `programMeta`** (whole-branch review, 23/10; **Ruling K′ in P2.2**). RAID lives in `projects/{pid}/raid/{programId}` docs (`items` = the v1 raid array). Writers name the role they act under with `viaProgramId` or `viaWorkstreamId`, so rules can check "any PM/Sub-PM of the project" without iterating a map. `programMeta` is Owner-only.
- **Gate before P2.2 deploys (blocker)**, moved earlier from "before P2.4":
  - **The problem:** the v1 project update rule lets a per-project `operator` or `owner` rewrite any project field. Once the v2 rules are live, writing `programMeta` / `memberUids` / `visibility` / `schemaVersion` would grant v2 rights. And because P2.2's read switch keys on `schemaVersion`, writing it would also flip the read path.
  - **Rules:** add an Owner-only rule for those four fields on the project doc. `programRaid` is writable by Owner and by any PM/Sub-PM of the project. Add emulator tests.
  - **Shim:** the v1 shim save takes those fields from the server copy (`ex`), the same way it already does for `relatedParties`, so a stale or old client cannot revert or drop them.
- **P2.4 checklist (additions):**
  - Assert the v2 sub-collections are empty, or reconcile them, before migrating a project.
  - Give duplicate and id-less tasks/workstreams/actions real unique ids before the switch; the dry-run must show 0 duplicates and 0 id-less items. This removes the need for a docId map in P2.3.
  - Project doc size must stay under ~900 KB (frozen v1 tree + `programMeta`).
  - Report actions with `workstreamId: null`; they are Owner-only in v2.
- **Before P2.3 writes:**
  - `activity` events: tie `createdAt` to `request.time`.
  - Action PIC: limit to an allow-list (status/Done, updates). Due date and title stay PM/Sub-PM only, because due dates drive performance.
  - Test `assigneeKeys` and the append-only `updates`/`checkIns` against the exact fields App.jsx writes from My Work.
- **Contributors (`contributorUids`), HOD decision 23/10:** a contributor may only append to `updates` (append-only, stamped `updatedBy`, `version`+1). They cannot change status, health or dates. Add the rule and tests in the pre-P2.2 gate. P2.1 rules currently give contributors no write rights.
- **Pilot projects:** AF 2026 Key Results and AF 2026 Operation have 0 tasks. Add Treasury 2026 (5 workstreams, 7 tasks) so the pilot exercises task rights. HOD to confirm before P2.4.

## P2.3 status (23/10/2026)
Code done on `feat/p2-3` (PR #20). Every item in "P2.3 must pick up" is closed. The `assigneeKeys` check was completed in the final-review fix wave (Ruling AE: `references`, `deadlineRequest`, `deadlineRequestHistory`).
- **Rules:**
  - Ruling P: the workspace Owner updates v2 project docs, and only the Owner may delete them.
  - Ruling Q: Decisions live in `decisions/{id}` docs, written by the Owner or any PM/Sub-PM via `viaProgramId` / `viaWorkstreamId`.
  - Ruling T: appended entries are suffix-preserving (App prepends), +1 per write, `authorUid == caller`.
  - Action PIC allow-list (status, completedAt, updates, subtasks; Ruling U). Activity `createdAt == request.time`.
  - Assignee may also edit `references` and request a deadline change (Ruling AE). Task delete is Owner-only (Ruling AF).
  - Ruling V: v2 project docs are readable per `canReadProject`. Ruling Z: a null list counts as `[]`.
- **Write path:**
  - The planner `src/planV2Save.js` diffs the tree against the loaded docs and stamps `authorUid` on new entries only (Ruling R). It refuses task deletes and history wipes (Ruling AA) and splits k new entries into k batches (Ruling X).
  - The executor `src/execV2Save.js` runs one transaction per batch, checks `version`, and reports ok / conflict / denied / error.
  - v2 activity is one doc per event (newest 500). The banner explains denied and refused saves and asks the user to reload after a denial (Ruling AB).
  - Ruling Y: ActionForm keeps fields it does not edit (fixes a pre-existing loss of `updates`/`subtasks`).
- **Membership and tooling:**
  - MembersModal keeps `memberUids` in sync with `arrayUnion` / `arrayRemove`.
  - `p2-pilot-copy --assignments` applies PM/Deputy/Sub-PM and workstream dates, with an old -> new preview, and adds every assigned uid and `picUid` to `memberUids` / `memberIds` (Ruling G).
- **Accepted until P3:**
  - An Assignee cannot close a task (A4) or resolve a blocker (Ruling W).
  - A denied edit stays in memory until the user reloads.
  - A PM of one program cannot move a task to another program.
  - `teamMembers` / `contributorRegistry` on v2 projects are Owner-only.
  - A manager's same-size rewrite can change `authorUid` (deliberate misuse only; ordinary saves keep stored stamps since the fix wave).
  - A mitigation PIC cannot mark a RAID mitigation Done or change its status; PM/Sub-PM do it (Ruling AG).
  - Renaming a program or changing its weight (`programMeta`) is Owner-only.
  - Reopening an Action via the form keeps its old `completedAt`.

## P2.4 status (25/10/2026)
Tooling done on `feat/p2-4` (PR #21, stacked on #20). Plan: `2026-10-24-p2-4-switch-real-projects.md`. Nothing has been written to production.
- **CLI `scripts/p2-migrate.mjs`** switches one project in place:
  - **Pre-checks:** size, nulls, order, raid shape, task links, `already-v2`, `non-plain-value`.
  - **Normalisation in memory** (P4-1, P4-2, P4-3).
  - **Writes:** sub-collections, then `programMeta` / `memberUids` / assignments / visibility. `schemaVersion: 2` comes last, in one transaction that checks `rev`, `writeId`, `memberIds`, `roles` and `visibility`, and sets the record to `switched` (P4-5).
  - **After the switch:** activity copy, with `createdAt` clamped to keep the v1 order (P4-8), then a verify (assemble + compare against the frozen v1 tree; emulator test MIG-2 runs the App's own read code, P4-10). The preview warns `member-not-active` for anyone who would lose read access (no active People-directory entry); the list is part of the hash.
  - **Migration record** at `workspaces/main/migrations/{pid}` (P4-4).
  - **Preview hash gate:** `--apply` needs `--expect <hash>` from the approved preview (P4-16), or `--expect post-flip` for a top-up.
- **Rollback** (`--rollback <pid>`) uses the same hash gate.
  - It refuses with exit 3 when v2 docs were edited.
  - `--force-with-report` writes the lost-data file first. `--delete-v2-docs` is opt-in.
  - It bumps `rev`/`writeId`, so stale v1 tabs see the conflict banner.
- **Rules:** clients can read or write v2 sub-collections only while the parent project is `schemaVersion 2`. The executor also refuses to write when the parent is v1. This stops stale v2 tabs from writing invisible data after a rollback.
- **Dry-run `--offline`** on the 22/10 backup: 7/7 projects round-trip, 0 blocking, 0 ids generated. Every project warns `no-members`, because the backup carries no `memberIds`; check member grants in the keyed preview.
- **Order:**
  - **Wave 1:** AF 2026 Key Results → AF 2026 Operation → Treasury 2026.
  - **Pilot:** 1–2 weeks.
  - **Gate before wave 2:** the v2 restore script P2.4b (P4-12).

## P2.4b status (04/11/2026)
Code done on `feat/p2-4b` (PR #24). Plan: `2026-11-04-p2-4b-v2-restore.md`. This is the gate before wave 2.
- **What it does:** `scripts/p2-restore.mjs` (`npm run p2:restore`) restores one v2 project from an in-app Backup JSON. The preview prints a hash, and `--apply --expect <hash>` refuses unless the hash matches.
- **What it never touches:** it never deletes a doc. Live items absent from the backup are kept, tasks as Dropped and actions as Cancelled. It never changes access fields or `schemaVersion`, and never rewrites activity; it adds one `project_restore` event.
- **Refusals:**
  - **History loss:** refused (exit 3) without `--allow-history-loss`. Lists that shrink (incl. `closeRequestHistory`) and lost keys of non-empty maps (e.g. `blockerResolutions`) count too. This covers lost comments, updates, check-ins, RAID items or mitigation actions, and any removed non-empty list or map field.
  - **Blocking codes:** `not-found`, `deleted`, `not-v2`, `backup-invalid`, `pid-not-in-backup`, `raid-not-array`, `live-orphans`, `live-id-mismatch`, `dotted-field`, `directory-unavailable`, `round-trip`, `doc-too-large`, `too-many-ops`.
  - **Runbook:** in PR #24 (backup → freeze → preview → written approval quoting the hash → apply → check screens + Credit, keep the snapshot → end freeze).
- **What the preview reports:** credit loss (a Completed task changed to another status), edited entries, fields removed per doc, and kept meta.
- **Apply sequence:**
  - Before any write, it saves a snapshot `p2-restore-before-<pid>-<stamp>.json` (gitignored). The same script can restore from it (test RS-7); RS-8 shows that `p2-migrate --rollback` then refuses without force.
  - It writes in one Admin transaction, which re-checks a live fingerprint (`STATE_CHANGED` if anything changed) and stays within 450 ops.
  - It writes a record at `workspaces/main/restores/{pid}_{hash}`, which no client can read.
  - It then verifies the result.
- **Known effect:** a decision or RAID doc that the restore updates loses its stored `viaProgramId`/`viaWorkstreamId` claims, so afterwards only the Owner can delete it.
