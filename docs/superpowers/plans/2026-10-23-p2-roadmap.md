# P2 — Server-side permissions: roadmap

P2 implements spec v2 §7–§9 (`docs/superpowers/specs/2026-10-14-roles-permissions-v2-design.md`). It is too large for one plan, so it ships as five sub-plans. Each one is a few small PRs and has its own gate. Each sub-plan is written in full only when the one before it has passed its gate, because later sub-plans depend on what the earlier ones teach us.

## HOD decisions (23/10/2026)
- **Q1:** Decisions and RAID stay in the project doc. Owner and any PM/Sub-PM of the project may write them.
- **A2/A3:** each program has 1 PM, with an optional Deputy PM who has the same rights. Each workstream has 1 Sub-PM; when it is empty, the PM covers it.
- **A4:** in P2, rules stop an Assignee from setting `Completed` or `Dropped`. Between P2 and P3, PM/Sub-PM close tasks; P3 adds "Submit as done" and the Approvals inbox.
- Earlier decisions still apply (spec §2.1): identity by uid, `ownerUids[]`, projects `restricted` by default, `wid` variable, rules tested on CI before every deploy.

## Contract fixed by P2.1 (binding for P2.2–P2.4)
Decided during P2.1 execution (23/10/2026). Each later sub-plan must cite this section.

- **Program data lives in `programMeta`.** Ruling C: `programMeta[programId]` holds every v1 program key except `workstreams` (name, raid, …) plus `order`, `pmUid`, `deputyUid`, `start`, `end`. The v1 `programs[]` and `actionItems[]` arrays in the project doc stay frozen for rollback and are never read in v2. `assembleProject` returns `{ project, orphans }`, and the read path must surface non-empty orphans.
- **Every v2 write must:**
  - stamp `updatedBy` with the writer's uid (Ruling I, enforced by rules);
  - set `version` to 1 on create and to `version + 1` on update (Ruling H, enforced). This includes an Owner restore/import over existing v2 docs.
- **Identity:** rules key on `picUid` only. `picEmail` is display and lookup data for invite-only people.
- **Owner checks:** Owner = uid in `ownerUids` OR the legacy `workspaceOwner` email until P2.5. In-app Transfer ownership stays locked while `ownerUids` is set (Ruling D); transfers go through the admin script until P2.5.
- **P2.4 checklist:**
  - Put every assigned `pmUid`, `deputyUid`, `leadUid` and every `picUid` into `memberUids` of restricted projects. Otherwise they can write but not read.
  - Doc ids for items without an id depend on position. Make the migration idempotent by keying on content or by recording the mapping.
  - The count report must also flag Owner-written tasks whose `programId` / `workstreamId` do not match a workstream doc.
- **RAID moves out of `programMeta`** (whole-branch review, 23/10). RAID is written by PM/Sub-PM (Q1), but `programMeta` must be Owner-only. So P2.2 changes the split: `programRaid[programId] = raid[]` becomes a separate project-doc map. `programMeta` keeps every other program key. Assemble re-merges RAID into each program.
- **Gate before P2.2 deploys (blocker)**, moved earlier from "before P2.4":
  - **The problem:** the v1 project update rule lets a per-project `operator` or `owner` rewrite any project field. Once the v2 rules are live, writing `programMeta` / `memberUids` / `visibility` / `schemaVersion` would grant v2 rights. And because P2.2's read switch keys on `schemaVersion`, writing it would also flip the read path.
  - **Rules:** add an Owner-only rule for those four fields on the project doc. `programRaid` is writable by Owner and by any PM/Sub-PM of the project. Add emulator tests.
  - **Shim:** the v1 shim save takes those fields from the server copy (`ex`), the same way it already does for `relatedParties`, so a stale or old client cannot revert or drop them.
- **P2.4 checklist (additions):**
  - Assert the v2 sub-collections are empty, or reconcile them, before migrating a project.
  - Give duplicate and id-less tasks/workstreams/actions real unique ids before the switch; the dry-run must show 0 duplicates and 0 id-less items. This removes the need for a docId map in P2.3.
  - Project doc size must stay under ~900 KB (frozen v1 tree + `programMeta`).
  - Report actions with `workstreamId: null`; they are Owner-only in v2.
- **Before P2.3 writes:**
  - `activity` events: tie `createdAt` to `request.time`.
  - Action PIC: limit to an allow-list (status/Done, updates). Due date and title stay PM/Sub-PM only, because due dates drive performance.
  - Test `assigneeKeys` and the append-only `updates`/`checkIns` against the exact fields App.jsx writes from My Work.
- **Contributors (`contributorUids`), HOD decision 23/10:** a contributor may only append to `updates` (append-only, stamped `updatedBy`, `version`+1). They cannot change status, health or dates. Add the rule and tests in the pre-P2.2 gate. P2.1 rules currently give contributors no write rights.
- **Pilot projects:** AF 2026 Key Results and AF 2026 Operation have 0 tasks. Add Treasury 2026 (5 workstreams, 7 tasks) so the pilot exercises task rights. HOD to confirm before P2.4.

## Rules for every sub-plan
- One small PR per purpose. Every PR states its data and rules impact and how to roll it back.
- Before any phase that touches data, HOD exports Backup JSON + Excel.
- Rules ship only with green emulator tests in CI.
- No mass refactor of App.jsx. The adapter keeps the in-memory tree shape.
