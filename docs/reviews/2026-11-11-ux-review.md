# AF-MPT — speed, save/error feedback and reliability as users feel it (read-only audit)

Date: 11/11/2026. Branch `feat/mindmap-roles` at `e325762`. Nothing was modified, deployed or written to Firebase.

Method: code reading (`src/App.jsx`, `src/storage-shim.ts`, `src/readV2.js`, `src/execV2Save.js`, `src/persistence.js`, `src/auth.tsx`, `src/main.tsx`, `src/data.ts`, `src/components/SearchModal.tsx`, `index.html`, `vercel.json`, `vite.config.js`), one `npm run build`, and one esbuild size measurement of `xlsx`. The app was **not** run in a browser, so every timing and every layout statement is an estimate from code and is marked "unverified". `npx vitest run` was not run (not needed for this angle).

Earlier reviews are referenced as B-n (`review-B-writes.md`) and C-n (`review-C-client-ops.md`). Their findings are not repeated, only linked where the user-facing symptom has the same root.

## Summary

Rendering is not what makes the app feel slow. At the current size (7 projects, largest 187 tasks) memoisation is adequate and no virtualisation is needed. What users feel comes from four places:

1. **Startup is a serial network waterfall** behind a bare "Loading workspace…" text: about 13 sequential Firestore round trips today, where 4 would do.
2. **Nobody learns that someone else changed something.** There is no refresh button, no check on tab focus and no polling. A tab left open is the main source of the "someone else changed it — reload, then redo your edit" banner on v1 projects.
3. **Saving is invisible when it works and a dead end when it fails.** There is no "Saving… / Saved" indicator. The network-error banner offers only Reload, which discards the edits it says "exist only on this screen", although a retry is safe by design.
4. **Read failures look like missing data** (the project shows as "(unknown)", no banner). Same root as C-H2 / B-3.

Bundle: 479 KB gzip JS. `xlsx` alone is 162 KB gzip of it and is needed only for import/export.

## A. Quick wins (each S, under half a day, one small revertible commit)

### A1. Load projects in parallel; stop blocking first paint on the activity log
- Symptom: "Loading workspace…" for several seconds on every open and every hard-refresh (hard-refresh is part of every runbook).
- Root cause: `src/App.jsx:12693-12697` loads projects one by one (`for … await loadProject(pid)`). A v2 project costs two sequential round trips (project doc at `src/storage-shim.ts:438`, then sub-collections at `:60-74`). Then `App.jsx:12700-12703` awaits the current project's activity before `setLoading(false)` at `:12717`. Before that, `loadMeta` reads the workspace doc and then the project list sequentially (`storage-shim.ts:395-400`). With 4 v1 + 3 v2 projects: 2 + 4 + 6 + 1 = **13 sequential round trips**.
- The `activity` state is used by one view only, Dashboard (`App.jsx:14115`).
- Change: `const loaded = await Promise.all(m.projectIds.map(loadProject))`; load activity after `setLoading(false)` (or only when Dashboard opens, see A2).
- Gain: 13 → 4 sequential round trips. At 80–150 ms per round trip (unverified, depends on the Firestore region) that is roughly 0.7–1.4 s off every load, and the gain grows with each project moved to v2.
- Risk: low. Per-project caches (`knownRev`, `v2Loaded`) are keyed by pid; `ownerUidsNow` uses the already-filled `wsMetaCache`.

### A2. Load activity only when Dashboard is opened; don't await it on project switch
- Symptom: clicking a task in My Work, or a search hit that lives in another project, feels sticky. Nothing happens until two network calls return.
- Root cause: `switchProject` (`App.jsx:13645-13659`) awaits `loadActivity` (v2: up to 500 doc reads, `storage-shim.ts:457-470`) and then `saveMeta` (a workspace-doc write). The callers at `App.jsx:14071-14076`, `:14077-14082` and `:14247-14250` all `await switchProject(...)` before `setSelectedTaskId` / `setView`.
- Change: in `switchProject` set state first, then fire the activity load and `saveMeta` without awaiting. Better: fetch activity in an effect keyed on `view === 'dashboard' && currentId`.
- Gain: navigation becomes instant (saves 2 round trips, about 200–600 ms, unverified). Saves up to 500 reads per switch and per startup on a v2 project, the same reads C-H1 counts.
- Risk: low. Guard against a late activity response for a project the user already left (compare the pid before `setActivity`).

### A3. "Saving… / Saved" indicator and a Retry button on the error banner
- Symptom: users cannot tell whether an edit has been saved. On a network blip the banner says "Your recent edits exist only on this screen — check your connection or permissions, then reload" (`App.jsx:2031`) and the only button is Reload (`:2036`), which throws those edits away.
- Root cause: `SaveBanner` renders failures only (`App.jsx:2022-2039`). `pendingSaves` is a ref, so nothing can render "saving" (`App.jsx:12664`, `:12965`). No retry path and no `online` listener exist (grep finds no `'online'`, `visibilitychange` or `setInterval` in `App.jsx`).
- Why retry is safe: an `'error'` state is cleared by the next `'ok'` (`persistence.js:27-38`). The v1 path recognises its own lost commit through `writeId` / `pendingWriteIds` (`persistence.js:83-88`, `storage-shim.ts:556-562`). The v2 path diffs against the last saved docs.
- Change:
  - A small chip in the top bar driven by one state value: "Saving…" while a save is pending or in flight, "Saved 10:42" after `'ok'`.
  - For `error` entries, a "Retry" button that calls `persistProject(projectsRef.current[pid])`; call the same on the `online` event.
  - New wording: "Couldn't save — your edits are still on this screen. Retry, or keep this tab open until the connection is back."
- Gain: trust, and it removes the main case where a user loses work by following the banner.
- Risk: low. Keep Reload as the only action for `conflict`, `denied`, `refused` and `history`.

### A4. Tell users when their view is old; check on tab focus
- Symptom: a user edits in a tab opened this morning. On a v1 project the first save is refused with the conflict banner and the edit must be redone after reload. Edits made by others never appear without a manual browser reload. Two tabs of the same user conflict with each other the same way.
- Root cause: no realtime sync, no refresh control, no focus/visibility handler (only `beforeunload` at `App.jsx:13011`). v1 uses one `rev` for the whole project (`persistence.js:14-17`), so any edit by anyone anywhere in the project makes every other open tab stale. Conflict is sticky (`persistence.js:35`): every later edit in that tab is also unsaved.
- Cheapest safe option within Spark:
  1. The top bar shows "Loaded 09:12 · Refresh". Refresh is `window.location.reload()`, allowed only when `hasUnsavedWork` is false (otherwise ask). It costs 0 reads until clicked. A full reload keeps the shim's "each project is loaded once" assumption (`storage-shim.ts:97-98`).
  2. On `visibilitychange` → visible, if the tab was hidden for more than 10 minutes and nothing is unsaved: one `getDoc` of the current project doc. If the v1 `rev` differs from the loaded one, show "This project was changed by someone else — Refresh". Cost: 1 read per return to the tab, e.g. 20 users × 20 returns = 400 reads/day (0.8 % of the 50k quota).
  3. v2 projects have no project-level change marker: the project doc is only touched when `metaPatch` is set (`execV2Save.js:89-93`). Option: one query `tasks where updatedAt > loadedAt limit 1` (1 read). Unverified: it needs `updatedAt` on migrated docs and a check that rules allow that list query. Until then, show only the "Loaded hh:mm" age for v2. v2 conflicts are per document, so a stale tab is far less harmful there.
- Do not add polling or `onSnapshot` on project data on Spark.
- Risk: low for steps 1 and 2. Reloading one project in place (without a page reload) is not recommended now: it would replace `v2Loaded` under an in-flight save.

### A5. Show a banner when a read fails instead of an empty or partial workspace
- Symptom: after a network or quota error a project silently disappears (the selector shows "(unknown)", `App.jsx:13916`), or My Work is simply missing items. Users believe data is lost.
- Root cause: every shared read error becomes `null` (`storage-shim.ts:488-491`, `App.jsx:1533`). The boot loop skips null projects without recording it (`App.jsx:12695-12696`). Same root as C-H2, B-2, B-3 / C-M7.
- Change (UX part only): collect the pids whose load returned null and show a persistent banner "Couldn't load: X, Y — Retry" (Retry = reload). The meta-null → seed path is B-3's fix and should ship with it.
- Gain: no false "data lost" reports. Risk: low.

### A6. Lazy-load `xlsx`
- Symptom: the first visit, and the first visit after each deploy, downloads and parses 479 KB gzip of JS.
- Root cause: `import * as XLSX from 'xlsx'` at `App.jsx:10`. There is no code-splitting besides `auth` (`vite.config.js` has no `manualChunks`).
- Build output:

| Chunk | Raw | Gzip |
|---|---|---|
| `App-*.js` | 1,064.84 KB | 305.25 KB |
| `index-*.js` (React + Firebase) | 659.75 KB | 173.53 KB |
| `auth-*.js` | 8.38 KB | 3.65 KB |
| `xlsx.mjs` alone (esbuild, minified) | 503 KB | 162 KB |

- `xlsx` is 53 % of the App chunk's gzip size.
- Change: replace the static import with `const loadXLSX = () => import('xlsx')` and `await` it in the 6 functions that use it (`App.jsx:1629`, `:1697`, `:5467`, `:5593`, `:9338`, `:11955`). Wrap the import in a catch that toasts "A new version is available — reload", because a tab opened before a deploy will get a 404 for the old chunk.
- Gain: 479 → about 317 KB gzip (−34 %) and about 0.5 MB less JS to parse on every load (roughly 100–200 ms on an office laptop, unverified). Returning users already get the files from cache (hashed assets), so the network gain is on the first load after each deploy.
- Risk: low. Export functions become async; they are called from click handlers.

### A7. Stop saving on every keystroke pause in the health note
- Symptom: typing in the amber/red health note can feel laggy on CRP, and each pause sends the whole project.
- Root cause: `App.jsx:3641-3646` calls `onUpdate` per keystroke → `applyTaskUpdate` → `cloneDeep` of the whole project (`:13280`) → `setProjects` → the whole App re-renders. `myWorkBadge` recomputes `computeMyWork` + `computeMyRaid` over all projects (`:12770-12777`), `deriveTeamMembers` reruns (`:12668`), and Outline recomputes credits (`:7062`). The save debounce is 400 ms (`:12979`), so each pause is one transaction: on v1, 1 read plus a full-document write (CRP ≈ 77 KB upload).
- Change: keep the text in local state and commit on blur (the pattern the rest of TaskDetail already uses with `draft`). Optionally raise the debounce at `:12979` from 400 to 800–1000 ms.
- Gain: one save per note instead of several, and no full-tree clone per key. Risk: low; the commit on blur must also fire when the panel closes.

### A8. Error boundary around the whole app; fix the boot error text
- Symptom: an exception in the task panel, top bar or any modal blanks the page (C-L4: the boundary wraps the main view only, `App.jsx:14060-14181`; TaskDetail at `:14183` is outside it). If the App chunk fails to download, users are told ".env.local is missing Firebase keys … Firebase Console" (`main.tsx:93-102`).
- Change: wrap `<App/>` in `main.tsx` with a boundary that says "Something went wrong. Your last saved changes are safe. Reload". Change the BootError copy to "Couldn't load the app. Check your connection and reload" with a Reload button, and keep the technical message in small print.
- Risk: none.

### A9. `users` listener: every app open is pushed to every open tab
- Symptom: none visible. Small read cost, and a full re-render in everyone's tab each time anyone opens the app.
- Root cause: `upsertCurrentUser` writes `lastSeen` on every sign-in resolution (`auth.tsx:48`, `data.ts:64-77`). `useUserDirectory` keeps an `onSnapshot` on the whole `users` collection (`data.ts:79-95`), and each update changes `directory` → `teamMembers` → App re-render.
- Change: write `lastSeen` only when the stored value is older than a day, or replace the listener with one `getDocs`.
- Gain: about (open tabs × loads per day) reads, e.g. 20 × 60 = 1,200/day (unverified usage), and no surprise re-renders. Risk: low.

### A10. Skip the duplicate project read at startup
- Root cause: the project list query downloads every full project doc just for id and name (`storage-shim.ts:399-407`), then each doc is fetched again (`:438`). v1 trees (CRP 77 KB) are downloaded twice.
- Change: keep the list query's snapshots in a short-lived map in the shim and serve the immediately following `project:` get from it.
- Gain: N reads (7 today) and N requests per load. With A1 the time gain is small.
- Risk: low to medium (it touches `knownRev` bookkeeping and needs a unit test).

### A11. Small copy and consistency fixes
- Search results can be up to 60 s old although the data is in memory: module cache with `CACHE_TTL_MS = 60_000` (`SearchModal.tsx:31`, `:84`). Remove the cache.
- The Restore confirmation still says "for everyone using this artifact" (`App.jsx:13818`).
- `saveMeta` failures are silent while the toast reports success (`App.jsx:12849-12872`, `:14057`). Check the boolean it returns.
- Sign-in errors show raw Firebase text such as `Firebase: Error (auth/popup-blocked).` (`auth.tsx:66-67`). Map `auth/popup-blocked` and `auth/network-request-failed` to plain sentences.
- Backup JSON has no progress state while it reads every activity log (`App.jsx:13810-13813`). Disable the button and show "Preparing backup…".

## B. Larger items

### B1. Small screens (M for the header, L for phone support)
- There is no `@media`, `matchMedia` or `innerWidth` anywhere in `App.jsx`, and no touch or pointer handlers (grep counts: 0).
- 1366×768 (unverified, not rendered): the top bar is one `flexWrap: 'wrap'` row (`App.jsx:13906`) holding the project selector, 6 icon buttons, the Focus selector, progress, 10 tabs (13 for the Owner, `:13951-13965`), Meeting / Briefing / Minutes / Excel / backup / restore and the account pill. Estimated content width is about 1,900–2,300 px, so it wraps to 2–3 rows and takes roughly 80–130 px of a ~650 px viewport, plus the Monday banner. The task panel defaults to 400 px (`uiPrefs.js:4`), leaving about 966 px for the view, which is fine.
- Phone:
  - The task panel has a 360 px minimum and `flexShrink: 0` (`App.jsx:3538`, `uiPrefs.js:2`), so on a 390 px screen the main view is squeezed to almost nothing.
  - Mind map pans with mouse events only (`:6620-6637`) and zooms with the wheel only (`:6639`).
  - Outline reorder is HTML5 `draggable` only (`:7308`), which does not fire on touch.
  - Dashboard / Credits / Team grids are fixed `repeat(4, 1fr)` (`:7423`, `:9370`, `:12027`).
- Minimal change for laptops (M): move Meeting / Briefing / Minutes / Excel / backup / restore into one "More" menu (`PopoverMenu` already exists) and let the tab strip scroll horizontally instead of wrapping.
- Phone (L): out of scope unless the HOD wants My Work on mobile. The cheapest step is opening the task panel in its existing "expanded" overlay mode when the window is narrower than about 800 px.

### B2. Instant paint for returning users (L, not recommended now)
- Firestore uses the default memory cache (`firebase.ts:30`, plain `getFirestore`). Only identity, current project id, panel width and My Work mode are in `localStorage`. A returning user always waits for the full load.
- `persistentLocalCache` would **not** make startup faster or cheaper: `getDoc` / `getDocs` still go to the server first when online. It would also keep queued offline `setDoc`s (activity, meta) across reloads, which makes B-3's scenario more durable. If C-H2's suggestion to enable it is taken, do it only after B-2 / B-3 are fixed.
- A stale-while-revalidate snapshot would have to be read-only until the real load finishes, because the save planner needs the real `rev` / `version` base. It is not worth it once A1 + A2 bring the load down to about 4 round trips.

### B3. Finish moving the remaining v1 projects to v2 (already planned)
- This is the real fix for conflicts. v1 refuses a save when anyone changed anything in the project; v2 refuses only when the same document changed (`execV2Save.js:66-72`). Until then A4 is the mitigation.
- Do A2 and C-H1 first so that v2 does not multiply reads.

### B4. Render performance (no action needed now)
- Checked: 84 `useMemo` calls. Outline weights and credits (`App.jsx:7044-7062`), Mind map tree / layout / edges (`:6544-6579`), Gantt rows (`GanttView.tsx:90-129`), Portfolio (`:8412`), Credit report (`:11881`) and My Work (`:11243`) are memoised on `project` / `projects`.
- There is no `React.memo` anywhere and App passes inline closures, so every App state change (toast, menu, banner) re-renders the active view. With 200 rows or fewer this is a few ms (unverified).
- Watch items if a project grows past about 500 tasks: `computeMyWork` runs twice per edit (badge at `:12772` and view at `:11244`); Outline does `findIndex` per row (`:7311`); Mind map pan sets state on every mouse move (`:6634`).

## C. Long sessions
- Listeners and timers are cleaned up: Modal keydown (`App.jsx:1855-1860`), panel resize (`:3269-3276`), mind map pan (`:6632-6637`), `beforeunload` (`:13011-13012`), Walkthrough (`Walkthrough.jsx:139-144`). **Mind map** (6540–6895). *Để làm gì:* nhìn toàn cảnh cấu trúc và tiến độ từng nhánh. *Rối ở đâu:* tên cắt 28 ký tự không xem được bản đầy đủ; task Pending approval trông như Planned; legend thiếu; chỉ sửa qua menu ⋯; zoom mặc định 0,8 (6562) nên chữ 13px còn ~10px, dòng phụ 10,5px còn ~8px; không dùng được bàn phím; "Delete program" hiện cho mọi người. *Cải tiến đáng giá nhất:* tooltip tên đầy đủ + màu cho Submitted (B1 + B3).

**Outline** (6897–7375). *Để làm gì:* nơi thật sự lập và sửa kế hoạch. *Rối ở đâu:* mỗi dòng header chen ~9 thứ (mũi tên, tên, PM, Deputy, weight, tỉ lệ, thanh tiến độ, 3 nút icon) và phải `flexWrap` khi có role; ô credit pool chiếm đầu trang; không lọc ngoài tìm tên; không sửa tại dòng. *Cải tiến đáng giá nhất:* 3 chip lọc (B22) — biến Outline thành màn làm việc hằng tuần của Sub-PM.

**Gantt** (`src/components/GanttView.tsx`). *Để làm gì:* xem lịch và chồng lấn. *Rối ở đâu:* Submitted và Dropped cùng màu Planned (572–577); chữ 10px trên thanh; token `subtle` cũ 3,07:1; task thiếu ngày bị loại mà không nói có bao nhiêu **[chưa xác minh — chỉ thấy thông báo khi không có task nào, dòng 155]**. Chỉ đọc là hợp lý vì End cần duyệt. *Cải tiến đáng giá nhất:* dòng "n tasks hidden (no dates)" — biến Gantt thành công cụ dọn dữ liệu.

**Dashboard** (7378–7500). *Để làm gì:* tình trạng một project: tiến độ, blocker, sắp đến hạn, quá hạn, update gần đây. *Rối ở đâu:* 4 thẻ + 6 panel, "Recent updates" và "Recent activity" gần nghĩa; văn bản cắt 200 ký tự; bấm task thì nhảy sang Outline; với 63% task quá hạn (SPEC §3) panel Overdue rất dài. *Cải tiến đáng giá nhất:* mở panel task tại chỗ (B21) và nhóm Overdue theo PIC.

**Portfolio** (8411–8427, Owner). *Để làm gì:* màn review tuần của HOD — heatmap sức khỏe, phân bổ khối lượng, mùa cao điểm, tín hiệu quá tải. *Rối ở đâu:* 4 khối xếp dọc, không có số việc chờ duyệt; bấm project không dẫn đi đâu thấy được; không chọn được làm màn mở đầu. *Cải tiến đáng giá nhất:* B12 + một thẻ "Pending approvals: n" dẫn sang A1.

**My Work** (11227–11860). *Để làm gì:* "hôm nay tôi phải làm gì". View tốt nhất của app: 2 chế độ, đổi status và viết update tại chỗ, Mentions, credit cá nhân, empty state tử tế. *Rối ở đâu:* 7 section; task gửi duyệt biến mất; người duyệt không có hàng đợi; "Decisions awaiting your input" và credit đứng ngang hàng với việc khẩn. *Cải tiến đáng giá nhất:* A1.

**Credits** (11862–12177, Owner). *Để làm gì:* bảng điểm đóng góp theo năm. *Rối ở đâu:* công thức chỉ được giải thích bằng một dòng trong Project Settings (14977); "cp", "projected", "earned", "weight" không có định nghĩa tại chỗ; ký hiệu ⚖ / ⚙ Auto / ✎ Manual (3740–3741) không chú thích. *Cải tiến đáng giá nhất:* khối "How credit is calculated" thu gọn được ở đầu trang (và trong glossary).

**Briefing / Minutes / Meeting** (12505–12577, 6357, 5769). *Để làm gì:* tạo tóm tắt tuần và biên bản để dán vào Gmail; Meeting là chế độ trình chiếu. *Rối ở đâu:* ba nút riêng trên header cho ba thứ gần nhau; luồng copy "Ctrl+C → mở Gmail → Ctrl+V" (1938–1941) nhiều bước; Meeting mode chỉ đọc. *Cải tiến đáng giá nhất:* nút "+ Action" trong Meeting mode mở `ActionCreateModal` có sẵn (review 14/10 #10, vẫn mở).

## 5. Những gì đang tốt (giữ nguyên)

- **My Work**: đúng mô hình "My Tasks" của thị trường, sửa nhanh tại chỗ, badge, empty state.
- **SaveBanner + stale-write guard**: lưu lỗi có báo (2022).
- **Panel task**: kéo rộng, nhớ độ rộng, expand, ô update tự giãn, tay kéo có `aria-label` (3541).
- **`DialogHost` tự viết** (2055–2140): confirm / prompt / alert thống nhất, Enter/Esc, nút danger.
- **Esc đóng đúng modal trên cùng** khi chồng nhiều lớp (1841–1862); `role="dialog"`, `aria-modal`.
- **Pill trạng thái có icon + chữ**, không chỉ dựa vào màu (1802–1813); Dropped có gạch ngang + mờ.
- **CloseControl**: nhãn rõ ("Submit as done", "Pending approval · người duyệt · since ngày"), Reject bắt buộc lý do, Reassign có `aria-label`.
- **RolePicker**: "— (Owner decides)" / "— (PM decides)" khi trống; badge "inactive"; `aria-label` theo phạm vi.
- **Xác nhận trước thao tác phá hủy** có đếm số task bị ảnh hưởng (6730, 6950).
- **Search toàn cục Ctrl/Cmd+K** qua project, task, update.
- **View as chỉ đọc** với banner rõ ràng.
- **Màu phân cấp Project/Program/Workstream** dùng chung giữa Mind map và Outline, đạt AA (8,60 / 5,46 : 1).
- **Export chống formula-injection** (1754–1760); import có cảnh báo PIC lạ.
- **Test contrast tồn tại** — nền tốt để mở rộng (B2).
